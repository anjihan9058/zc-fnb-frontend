# 원가·재무 분석 확장과 백엔드 응답 계약

2026-10-29. 기존 화면을 확장했고 별도의 AI 최상위 메뉴나 라우트를 만들지 않았다.

## 접근 위치와 레이아웃

- 메뉴·원가 → **전월 비교 · AI 원가 분석** → 기존 `/reports?view=cost`.
- 기존 보고서의 메뉴·원가 분석 선택에서도 동일한 화면을 사용한다. 기존 등록 메뉴의 최근 단가 조회는 이 화면 아래 펼침 영역으로 유지했다.
- 홈의 대시보드 선택 → **재무 현황** → 기존 `/dashboard/financial`.
- 기존 사이드바·상단 바·대시보드 선택·재무 바로가기·매입 문서/연결 현황은 유지했다.
- 로컬 `Restaurant365_UI_Part1_Dashboard_OCR/restaurant365_ui_reference/images/01_layout/R024_financial-dashboard.png`를 직접 확인했다. 상단 바로가기 뒤 기간·사업장 조건과 KPI를 배치하는 구조를 참고했고, 차트·분석 카드는 현재 ZC FNB의 색상·글꼴·간격 토큰을 사용한다. 원본 이미지를 배포 자산으로 복제하지 않았다.

## 구현과 데이터 경계

| 계층 | 파일 | 역할 |
|---|---|---|
| 계약·계산 | `src/shared/analytics.ts` | 월 이동, 레시피 원가, 기여도 분해, 증감률, 재무 집계 |
| 가상 자료 | `src/mocks/analytics.ts` | 사업장·월별 가상 스냅샷, 수치에서 생성하는 분석 문장 |
| 선택 상태 | `src/app/useAnalysisPreview.ts` | 사업장별 자료, 기준 월, 가상/미연결 보기 |
| 공통 UI | `AnalysisCommon.tsx` | 기간 필터, 출처 표시, 증감률, 근거·한계가 있는 분석 카드 |
| 원가 | `MenuCostAnalysis.tsx` | 월별 메뉴 비교, 재료 단가 효과, 판매가 시뮬레이션 |
| 재무 | `FinancialAnalysis.tsx` | KPI, 추이 선 그래프, 비용 비중 누적 막대, 전월/당월 비용 막대, 종합 분석 |

기본 데모 모드에서는 가상 자료를 표시한다. 기존 실제 API 모드에서는 분석 자료 미연결이 기본이며 가상 보기를 명시적으로 선택할 수 있다. 가상 분석은 현재 저장된 구매·급여·레시피 기록에 쓰거나 섞지 않는다. 사업장 변경 시 자료 키와 선택 월을 갱신하며, 가상 값은 같은 사업장·같은 월에서 재현 가능하다.

**AI 카드는 실제 모델 응답이 아니라 규칙으로 생성한 가상 응답 예시**다. API 경로를 임의로 만들거나 새 네트워크 호출을 추가하지 않았다. 문장은 비교 월의 동일한 계산 결과에서 생성하고, 단가·비용의 동반 변화만으로 인과를 확정하지 않는다. 가격 변경·발주 등 행동을 강요하는 문구도 넣지 않았다.

## 계산 기준

- 레시피 식재료 원가: 재료별 `round(정규화 사용량 × 해당 월 단가)` 합계. KRW 원 단위 반올림.
- 원가율: 식재료 원가 / 해당 월 판매가격 × 100.
- 예상 식재료 마진율: (가정 판매가 − 식재료 원가) / 가정 판매가 × 100. 판매가 시뮬레이션은 실제 가격을 저장하지 않는다.
- 원가율 차이: 당월 원가율 − 전월 원가율, **%p** 단위. 금액의 증감률과 구분한다.
- 재료 단가 효과: 당월 사용량으로 계산한 당월 단가 금액 − 당월 사용량으로 계산한 전월 단가 금액. 동일 재료·동일 단위·전월 레시피가 있는 경우만 분류한다.
- 구성·미분류 효과: 실제 메뉴 원가 차이 − 확인 가능한 단가 효과 합계. 신규·제거 재료, 사용량 변경, 비교 단위·단가 부족 등을 여기에 남긴다.
- 상승 기여 비중: 각 양의 단가 효과 / 양의 효과 합계 × 100. 인하 효과는 상쇄로 별도 표시한다. 표시 자릿수 반올림으로 비중의 화면 합계가 소폭 달라질 수 있다.
- 재무 매출: 할인·취소·환불을 반영하고 부가세를 제외한 순매출. KPI의 총매출에도 이 기준을 명시한다.
- 총 운영비용: 식재료비 + 인건비 + 기타 운영비. 구매금액을 식재료 사용 원가로 대신 넣지 않는다.
- 영업손익: 순매출 − 총 운영비용. 모든 항목과 운영비 완결성이 확인될 때만 계산한다. 금융비용·세금 등을 반영한 순이익은 만들지 않는다.
- 운영비 미완료 시에는 계산 가능한 매출총이익(순매출 − 식재료비)까지만 표시한다.
- 전월 대비 증감률: (당월 − 전월) / |전월| × 100. 전월이 음수이면 절댓값 기준임을 표시한다. 전월 0원·누락은 임의 비율을 만들지 않는다.
- 비용 구성은 매출을 분모로 하며 비용이 매출을 초과해도 100%로 잘라내지 않는다. 누락값은 0원으로 대체하지 않고 차트에 빈 구간으로 남긴다.

가상 식재료비는 예시 판매수량 × 레시피 소요 원가에 가정 폐기비를 더해 구성했다. 실제 재고 평가나 장부 결산 결과가 아니다. 가상 당월 숫자는 월간 예시이며 실제 현재일까지의 매출이 아니다.

## 백엔드에서 필요한 응답 데이터

엔드포인트·인증 계약은 백엔드와 합의할 영역이다. 아래는 프론트가 사용할 **응답 필드 목록**이며 실제 호출 계약 확정이나 서버 구현 완료를 뜻하지 않는다.

### 공통 메타데이터 (`AnalysisDataset`)

| 필드 | 형식·의미 |
|---|---|
| `schema_version` | 현재 1 |
| `workspace_id` | 인증·권한 검증된 사업장 ID |
| `currency` / `timezone` | KRW / Asia/Seoul |
| `source` | demo 또는 api. 표시 출처를 구분 |
| `generated_at` | 자료 생성·집계 시각 ISO 문자열 |
| `financials` | 월별 재무 기록. 동일 사업장·월 중복 금지 |
| `costs` | 월별 원가 스냅샷. 전월과 당월 모두 필요 |

### 월별 재무 (`FinancialMonth`)

- `month`: YYYY-MM.
- `net_sales`: 취소·환불·할인과 부가세 기준을 맞춘 월 순매출, KRW 또는 null.
- `food_cost`: 해당 기간 식재료 사용 원가, KRW 또는 null. 매입 합계와 구분해야 한다.
- `labor_cost`: 급여·시급 및 실근무 기준으로 집계한 인건비, KRW 또는 null.
- `expenses[]`: `{id, name, amount}` 형식의 임대료·공과금·수수료 등 기타 운영비.
- `operating_expenses_complete`: 기타 운영비 범위가 완결된 경우만 true. 단순히 일부 비용이 존재한다고 true로 보내면 안 된다.
- 모든 금액의 null은 미연결/미확정, 0은 확인된 0원이다. 운영비 0원도 명시적으로 0원 항목을 제공한다.

추가 합의 권장 메타데이터: `food_cost_basis`(재고 기반/이론 원가), 원천 문서·POS·급여 ID, 집계 범위와 마감 상태, 부가세 정책, 누락 항목 목록, 재집계 시각. 실제/추정 원가를 구분할 근거가 필요하다.

차트 12개월과 각 월의 전월 비교를 지원하려면 충분한 이전 기간을 제공해야 한다. 프론트는 월별 누락을 빈값으로 유지한다.

### 월별 원가 (`CostSnapshot`)

- `month`: YYYY-MM.
- `ingredients[]`: `{id, name, unit, unit_price}`. 표준 식재료 ID와 단위별 월 단가. 가격의 평가 기준(평균/최근/가중평균)은 서버와 고정한다.
- `menus[]`: `{id, name, selling_price, ingredients:[{ingredient_id, quantity}]}`.
- `quantity`는 위 식재료 단위에 맞게 정규화된 사용량이어야 한다. kg/g·L/mL 변환 후의 값이며 포장 단위 변환 정보가 없으면 비교 불가로 남긴다.
- 메뉴 ID와 식재료 ID는 기간 간 안정적으로 유지한다. 레시피 구성·판매가가 바뀌었으면 해당 월의 스냅샷을 보낸다.
- 가격·사용량이 없거나 해당 월에 미등록인 메뉴는 이전 값으로 임의 채우지 않는다.

### AI 분석 응답 (`AnalysisInsight`)

- `workspace_id`, `month`: 요청한 사업장·기준 월과 일치해야 한다.
- `origin`: `api-ai`. 현재 가상 응답은 `demo-rule`로 구분한다.
- `title`, `summary`: 객관적인 변화 설명. HTML이 아닌 일반 텍스트.
- `evidence[]`: `{label,value}`. 화면 집계와 같은 기준의 근거 값. 추후 원천 데이터 필드·문서 참조 ID도 합의한다.
- `limitations[]`: 누락 데이터, 추정 범위, 인과 판단 제한 등.
- 실제 연결 전 합의할 추가 필드: 비교 기간, 메뉴 ID(원가 분석), 데이터 스냅샷 버전, 생성 시각, 분석 상태/오류, 사용한 근거 참조 ID. 이전 사업장·기간의 지연 응답이 새 화면을 덮어쓰지 않도록 요청 키와 응답 키를 확인해야 한다.

실제 어댑터를 붙일 때 가상 팩터리를 교체하고, 서버 AI 응답을 표시한다. 이때 기존 등록 메뉴 ID와 스냅샷 ID를 연결하고, 데이터 출처 표기도 API로 바꾼다.

## 확인 범위

계산과 UI 연결을 위한 신규 테스트에서 누락값·전월 0원·적자·판매가 0/음수·월/사업장 변경·기여도 합계·차트 기간·네트워크 미호출을 확인했다.

- 신규 검사 20개(계산·자료 17개, UI 연결 3개) 통과.
- 전체 회귀 검사: **16개 파일, 151개 테스트 통과**. 빌드와 병렬 실행한 첫 검사에서 기존 인증 테스트 1건이 5초 제한으로 시간 초과했다. 빌드 종료 후 작업자 1개로 전체를 분리 실행해 모두 통과했으며 기존 테스트의 제한 시간은 수정하지 않았다.
- TypeScript `tsc -b` 통과, Vite 프로덕션 빌드 성공. 최신 `dist/`와 서비스 워커 생성.
- PWA manifest·아이콘 크기·서비스 워커·HTML 링크 정적 검사 통과.
- 빌드 경고: Zod 의존성의 주석 안내, main/ExcelJS의 큰 청크 안내. 빌드 오류는 없다.
- 브라우저 도구는 로컬 페이지 탐색에서 시간 초과가 발생해 PC·모바일의 실제 렌더 캡처는 완료하지 못했다. UI 연결 검사는 차트에 전달되는 자료와 사용자 선택의 동기화를 검사하며 실제 차트 렌더·툴팁의 시각 확인과 구분한다.
- 실제 백엔드·AI는 미연결이다. 이번 변경은 로컬 소스·빌드에 반영했으며 GitHub 업로드나 Vercel 재배포는 실행하지 않았다.
