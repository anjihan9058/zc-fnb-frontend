## 채팅

- PC와 모바일 모두 바깥 대시보드 헤더·메뉴 공간을 접고 채팅을 화면 전체에 표시합니다. PC는 채팅방 목록과 대화를 나란히, 모바일은 목록과 대화를 전환합니다.
- 푸른 대화 배경, 상대의 흰 말풍선, 내 노란 말풍선, 날짜 구분과 말풍선 옆 시간, 연속 메시지 묶음을 적용했습니다. 읽음 수·팀원 수·접속 상태를 임의로 만들지 않습니다.
- 대화만 스크롤하고 상단 채팅방 제목과 하단 입력창을 유지합니다. 모바일 키보드가 바꾸는 visualViewport 높이를 반영합니다. 이전 대화를 읽는 중 새 메시지가 도착하면 이동 버튼을 표시합니다.
- 채팅방 검색·추가, 대화 검색, 사진·PDF 첨부, 촬영, 이미지 원본 보기, 이모지 입력을 추가했습니다. PC Enter는 전송, Shift+Enter는 줄바꿈입니다. 모바일 Enter는 줄바꿈이며 전송 버튼으로 보냅니다.
- 영수증 분석과 일반 사진·PDF 첨부는 별도 선택입니다. 일반 사진 첨부는 OCR을 시작하지 않습니다. 영수증은 기존 합의대로 형식을 먼저 선택해야 전송됩니다.
- 메시지 최대 50,000자. 첨부는 JPG·PNG·WebP·PDF, 최대 10MB. 실제 메시지 전달과 권한은 서버 연동 대상입니다. 현재는 4초 메시지 폴링이며 WebSocket이나 카카오톡 연동을 구현한 것은 아닙니다.

## 텍스트 근무표 → 쉬프트

채팅에 직원별 날짜·시각이 적힌 긴 근무표를 붙여 보내면 말풍선의 **근무표로 정리**를 누를 수 있습니다. 전송 전 입력창의 **정리하기**, 근무표 화면의 **텍스트 붙여넣기**에서도 같은 대화상자를 엽니다.

1. 원문에 없는 근무 연도를 직접 입력합니다.
2. 직원 이름별로 기존 직원을 연결하거나 새 직원 등록을 명시적으로 선택합니다. 미등록 직원을 일괄 등록하는 옵션도 직접 선택해야 적용됩니다.
3. 직원별 근무 횟수, 출퇴근 시각 합계, 원문 기재 합계를 표시하고 차이가 있으면 알립니다.
4. 쉬프트 초안을 생성합니다. `15:00 ~ 00:30`처럼 종료 시각이 앞서면 다음 날 퇴근으로 만듭니다. `24:00`도 다음 날 00:00으로 보관합니다. 시작과 종료 시각이 같은 행은 24시간 해석에 대한 원본 확인 경고가 있습니다.
5. 원문, 연도, 원문 행별 시간·직원별 합계를 초안에 보관합니다. 휴게 시간이 원문에 없으면 null로 유지합니다. 사용자가 원본을 보고 휴게 시간을 일괄 입력하거나 행별로 보완합니다.
6. 직원 필터, 직원별 출퇴근 합계·실근무 합계, 행별·전체 원본 확인 체크 후 초안을 저장하고 확정합니다. 누락 값과 겹친 일정은 확정을 막습니다.

지원 예시:

```text
10월 우리 가게 근무
직원 이름
10/1 15:00 ~ 00:30 9.5
10/2 18:00~22:00 4
총 근무시간 : 13.5
```

해석할 수 없는 줄이나 잘못된 날짜·시각은 초안 생성 전에 표시합니다. 원문에 적힌 시간과 시각 차이만으로 휴게 시간을 추정하지 않습니다. 텍스트 형식 파서는 데모에서 동작하며, 실제 API 모드에서는 백엔드에 원문과 선택한 연도·직원 연결을 전달합니다. OCR/LLM 비밀키나 외부 AI 호출은 사용하지 않습니다.

텍스트에서 생성한 문서는 바로 `NEEDS_REVIEW`가 됩니다. 확정 전까지 실제 일정에는 반영하지 않습니다. 동일한 원문 메시지·연도 또는 동일 원문·연도의 재요청은 데모에서 기존 문서를 반환합니다.

엑셀은 확정 일정 상세와 직원별 합계를 두 시트로 만듭니다. 야간 근무가 혼동되지 않도록 시작·종료 날짜를 모두 포함합니다. 시간은 한국 시간 기준이며 휴게 시간이 없는 행의 실근무 값을 임의로 계산하지 않습니다.

## 메뉴·레시피와 원가

- `/menus`에 메뉴명, 판매가격, 1인분 식재료·사용량·구매 단위 등록·수정·삭제를 추가했습니다. 레시피나 판매가격 없이 메뉴 이름만 먼저 저장할 수 있습니다.
- 구매 단위가 kg이면 150g 사용량을 0.15kg로 입력합니다. 포장·규격 간 단위 변환은 하지 않습니다.
- 데모 계산은 해당 사업장의 **승인된 구매 이력** 중 같은 품목·단위의 최근 단가를 사용합니다. 가격 승인 후 쿼리가 갱신되면 메뉴 원가도 갱신됩니다.
- 식재료 원가는 사용량×구매단가의 합계입니다. 원가율은 원가/판매가격, 예상 식재료 마진율은 (판매가격−원가)/판매가격입니다. 인건비·임대료·수수료·포장비는 제외합니다.
- 어떤 재료든 확정 단가가 없으면 원가 합계를 미설정으로 남깁니다. 판매가격이 없으면 비율을 계산하지 않습니다. 원가 0이나 임의의 과거 단가로 채우지 않습니다.
- 원가 변화 비교는 현재 레시피 수량에 각 재료의 직전 구매단가를 적용한 비교값입니다. 당시 레시피를 복원한 과거 원가가 아닙니다. 직전 단가가 없는 재료가 있으면 비교값을 비웁니다.
- 대시보드에 메뉴별 원가율·예상 마진율과 원가 상승 메뉴를 연결했습니다. API 모드에서는 서버가 반환한 계산 결과를 표시합니다.

## 입고 검수

`/receiving`은 분석이 끝난 영수증을 수량 검수 대상으로 보여줍니다. 실제 수량, 오배송 여부, 비고, 입고일과 담당자를 입력하고 초안 저장 후 검수 확정을 할 수 있습니다. 누락과 초과 수량·오배송에는 비고를 요구합니다. 단가가 없어도 수량 검수는 가능합니다.

검수 데이터는 영수증 가격 승인과 독립적입니다. 검수를 완료해도 구매 이력이나 메뉴 원가를 변경하지 않습니다. 원본 수량이 바뀌면 오래된 검수 내용의 저장을 거절합니다. 완료 기록은 현재 UI에서 수정하지 않습니다.

## 로그인과 데이터 보관

`/login` 화면을 추가했습니다. 데모는 별도 계정 인증 없이 데모 시작을 제공하고, 실제 API 모드는 쿠키 세션 조회·로그인·로그아웃 계약을 사용합니다. 비밀번호를 브라우저 저장소에 저장하지 않습니다. 실서버 인증과 접근 권한이 구현·연동된 것으로 간주하지 않습니다.

기존 영수증·근무표 저장소를 유지합니다. 메뉴·입고 데이터는 사업장별 `zcfnb-operations-v1` 키에 추가 저장합니다. 기존 메시지에는 방 ID를 보완하며 새 채팅방도 같은 사업장의 영수증·근무표 흐름에 연결합니다. 기기 간 공유는 서버가 담당합니다.

## 추가 API 계약 제안

아래는 실제 서버에서 확인된 명세가 아니라 구현 어댑터의 협의용 계약입니다. 경로는 기존 API 기본 주소(`/api/v1` 등)에 상대적입니다. 일반 업무 API는 `X-Workspace-Id`와 인증 쿠키를 사용하며 서버가 사업장 권한을 확인해야 합니다.

| 메서드·경로 | 요청 | 반환 |
|---|---|---|
| GET `/auth/me` | 쿠키, 사업장 헤더 없음 | `SessionUser` 또는 401 |
| POST `/auth/login` | `{email,password}`, 사업장 헤더 없음 | `SessionUser` + 서버 인증 쿠키 |
| POST `/auth/logout` | 쿠키, 사업장 헤더 없음 | JSON 또는 204 |
| GET `/chat/rooms` | 없음 | `ChatRoom[]` |
| POST `/chat/rooms` | `{name}` | `ChatRoom` |
| POST `/rooms/{id}/messages/attachments` | multipart `file` | 첨부 정보를 포함한 `Message` |
| POST `/work-schedules/from-text` | `ScheduleTextImport` | `{schedule_id}` |
| GET `/menus/costs` | 없음 | `MenuCost[]` |
| POST `/menus` | `MenuRecipe` 전체 + `version` | 저장한 `MenuRecipe` |
| DELETE `/menus/{id}` | `{version}` | JSON 또는 204 |
| GET `/receiving` | 없음 | `ReceivingDocument[]` |
| PATCH `/receiving/{receipt_id}` | `{version,received_on,checked_by,completed,lines:[{item_id,actual_quantity,wrong_item,note}]}` | 서버가 계산한 `ReceivingDocument` |

타입: `src/shared/auth.ts`, `src/shared/types.ts`, `src/shared/schedules.ts`, `src/shared/operations.ts`.

`ScheduleTextImport`는 `{text,room_id,year,source_message_id?,employees:[{raw_name,employee_id,create}]}`입니다. 서버는 원문 해석·직원 등록과 문서/메시지 생성을 일관되게 처리하고, 재요청으로 중복 일정을 만들지 않아야 합니다. `WorkSchedule`의 `source_text`, `source_message_id`, `import_year`, `source_notes`, `reported_totals`를 상세 화면에 사용합니다.

`Message.attachment`는 `{name,type,size,url}`입니다. URL 권한·파일 종류·크기·업로드 검사를 서버에서도 수행해야 합니다. `ChatRoom`은 `{id,name,created_at}`이고 사용자·사업장 범위의 목록입니다. 메시지와 문서 생성의 접근 권한은 서버가 검증합니다.

`SessionUser`는 `{id,display_name,email?}`입니다. 최초 미인증 진입은 로그인 후 허용된 원래 경로로 돌아갑니다. 작업 중 401은 현재 입력을 유지하는 재인증 모달로 처리합니다. 같은 계정 로그인 후 기존 화면에서 이어가며 다른 계정은 캐시를 비우고 대시보드로 이동합니다. 별도 도메인 사용 시 쿠키·CORS·CSRF 정책 합의가 필요합니다.
