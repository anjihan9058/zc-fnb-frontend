# Restaurant365 참고 검토 — ZC FNB

검토일: 2026-10-28. 범위: Restaurant365 공식 공개 제품 안내·사용 문서와 현재 프론트 소스 비교. 로그인한 고객 환경에서 실제 업무를 수행한 검증은 아니다. 공식 문서의 일부 이미지가 불러와지지 않아 픽셀 단위 화면 비교는 하지 않았다. 아래 제안은 구현 완료 항목이 아니다. 이번 작업에서 앱 코드나 서버 설정은 변경하지 않았다.

## 제품 방향

ZC FNB는 직원들이 일상적으로 사용하는 팀채팅에서 자료를 올리고, 정리된 결과를 확인해 매장 운영 기록으로 연결하는 제품으로 잡는다. Restaurant365에서는 운영·회계 데이터를 연결하는 구조와 검토 방식을 참고한다.

Restaurant365에도 [개인·그룹 메시징, 읽음 확인, 반응](https://docs.restaurant365.com/docs/r365-messaging)과 [문서 OCR·초안 검토](https://docs.restaurant365.com/docs/documents-to-process)가 있다. 따라서 ‘채팅과 OCR이 있다’만으로 차별성을 설명하기는 어렵다. 이번에 읽은 공식 자료에서는 자유롭게 쓴 채팅 근무 내역을 구조화하는 동일한 흐름을 확인하지 못했지만, 경쟁사에 없는 기능이라고 단정할 수는 없다.

우리가 검증할 가설은 ‘직원에게 새 입력 양식을 요구하지 않고, 평소 올리던 한국어 근무 내역과 영수증을 활용해 재입력과 오류 수정을 줄일 수 있다’이다. 이를 입증하려면 완료까지 걸린 시간, 직접 고친 필드 수, 중복 등록 건수, 추출 정확도와 검토 후 확정 정확도를 따로 측정한다.

## 먼저 수정할 구체적인 부분

### 1. 채팅이 업무의 출발점이자 결과 확인 장소가 되도록

- 일반 대화는 편하게 유지한다. 명확한 영수증 첨부/근무표 정리 동작이나 사용자의 확인 없이 모든 대화를 업무 데이터로 바꾸지 않는다.
- 현재 긴 근무표 원문의 접기/펼치기와 정리 버튼은 유지한다. 여기에 ‘8명 · 90개 근무 · 합계 확인 필요 2건’ 같은 구조화된 요약 카드를 보완해 검토 화면을 연다. 숫자는 실제 분석 결과로만 표시한다.
- 영수증 카드에는 거래처·날짜·합계·품목 수·현재 상태·검토 버튼을 제공한다. 분석 완료/승인/실패에 따라 같은 카드의 상태를 갱신한다.
- 원문 메시지 ↔ 초안 ↔ 확정 결과를 왕복할 수 있게 연결한다. 근무표에는 현재 `source_message_id`가 있지만 영수증 모델에는 같은 필드가 없다. 공통 출처 연결 계약이 필요하다.
- 한 원문에서 여러 사람이 정리 버튼을 눌러도 결과가 중복 생성되지 않아야 한다. 수정된 메시지가 이미 확정한 기록을 조용히 덮어쓰지 않도록 버전과 재정리 정책을 둔다.

### 2. 실사용 채팅과 권한을 우선 완성

현재는 로컬 데모이고 메시지는 4초 폴링 구조다. 기기 간 공유·인증·사업장 권한은 실제 서버 연결이 필요하다. 실사용을 위해 메시지 식별자/전송 확인, 실패 재전송의 중복 방지, 이전 대화 페이지 조회, 읽음 위치, 새 메시지 알림을 먼저 합의한다. 실시간 전달은 WebSocket이나 SSE 등 서버 지원에 맞춰 정한다.

직원·점장·사장의 열람/수정/승인 권한도 필요하다. 공용 채팅방에 올린 원본 영수증의 공개 범위와 원가·은행 정보의 공개 범위를 별도로 정의한다. 권한은 서버에서 검사한다. 전체 직원에게 원가·급여·은행 내역을 자동으로 공개하지 않는다.

### 3. 홈과 원가 화면의 정보 밀도 개선

- 홈 첫 화면은 미처리 업무, 오늘 일정, 최근 가격 변동 순서로 구성한다. 현재 `DashboardPage.tsx`의 가격 이력은 `onion`/`kg`에 고정되어 있으므로 실제 등록 품목 선택 또는 가격 상승 상위 품목으로 바꾸는 것이 우선이다.
- 메뉴별 식재료 원가율과 ‘식재료만 반영한 예상 마진’을 유지하고 계산 범위를 숫자 가까이에 표시한다. 현재 계산은 인건비·임대료·수수료 등을 포함하지 않는다.
- 목표 원가율은 매장/메뉴에서 설정한다. 임의의 업계 기준을 정상·위험 판정으로 고정하지 않는다.
- 원가 변화에서 영향을 준 식재료와 구매 기록으로 이동한다. 당시 레시피·단가를 저장한 이력이 없으면 현재 레시피로 재계산한 비교값임을 표시한다.

### 4. ‘확정’의 의미를 나누기

영수증 검토 승인, 실제 입고 검수, 대금 지급, 근무 일정 게시, 실제 근무 확인은 서로 다른 상태다. 현재 가격 승인과 입고 검수의 분리는 유지한다. 근무표 예시처럼 지난 근무 시간을 합산한 글을 미래 일정으로만 취급하지 않도록 입력 목적을 구분한다. 예정 시간만으로 실제 출근이나 급여 지급을 확정하지 않는다.

### 5. 은행·회계 확장 전 데이터 준비

영수증에 문서 번호·총액·세액·공급가액·할인/배송비와 지급 연결을 추가할지는 백엔드와 합의한다. 거래 총액과 품목 합계 비교는 해당 필드가 실제로 제공되는 경우에만 적용하고, 없는 값은 추측하지 않는다.

은행 거래와 영수증은 일대일 외에 합산 지급·분할 지급·환불이 있을 수 있다. 매칭 후보와 확정 연결을 구분하고, 은행 내역을 새 비용으로 만들면서 기존 영수증 비용도 중복 집계하지 않도록 원본 거래를 연결한다. Restaurant365에서 국내 은행을 같은 방식으로 지원하는지는 이번 조사로 확인하지 않았다. 국내 연동 제공자와 지원 범위 검토가 별도로 필요하다.

## 권장 순서와 작업 구분

| 순서 | 작업 | 프론트에서 가능한 범위 | 서버·외부 의존 |
|---|---|---|---|
| 1 | 실사용 채팅 + 원문/추출/확정 연결 | 카드·미리보기·상태·원문 이동 | 인증, 공유, 메시지 전달·알림, 권한, 중복 방지, OCR/추출 |
| 2 | 홈의 처리할 일 + 검토 화면 개선 | 배치·필터·일괄 검토·고정 동작 | 업무별 미처리 집계·처리자·활동 이력 |
| 3 | 원가 근거 + 단위 환산 + 목표 원가율 | 입력·표시·근거 링크 | 규격, 서버 계산, 단가/레시피 이력 |
| 4 | 예정/실제 근무 구분 + 일간 보기 | 화면·필터·확인 흐름 | 유형, 게시/확인, 수정 이력·알림 |
| 5 | 거래처·비용·지급 내역과 파일 내보내기 | 목록·분류·지급 연결 화면 | 거래·지급 모델·권한·내보내기 계약 |
| 6 | 은행 거래 가져오기·증빙 매칭 | 업로드·추천 검토 UI | 파싱, 중복 방지, 매칭·장부 연결, 금융기관 연동 |
| 7 | POS·재고 기반 실제/이론 원가·손익 | 보고서·원인 분석 화면 | POS 판매, 재고·폐기·이동, 인건비·비용, 회계 기준 |

기존 원본 비교·문제 우선 검토·근무표 전체 요약·야간 처리·겹침 검사·엑셀·사업장 전환·입력 보호는 유지한다. 광범위한 메뉴를 추가하기보다, 팀원과 사장이 ‘대화에 올림 → 요약 확인 → 오류 수정 → 확정 → 원가/일정 반영’까지 실제로 끝낼 수 있는 흐름을 먼저 완성한다.
